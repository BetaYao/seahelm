共享核心，统一行为

业务规则与状态由 core 提供；客户端负责展示与交互。seahelm-gateway 统一外部接入、身份校验与连接管理，内部按 Web、Telegram 等渠道拆分模块。core 决定该不该通知（去重、冷却、卡片已在屏上就不再提醒），各端只负责投递：桌面横幅、Telegram 经 gateway。

会话独立，任务持续

seahelmd 保持终端与进程存活。桌面客户端可直连终端数据，远程浏览器通过 Gateway 转发。状态有两路来源：seahelmd 的屏幕快照与 OSC 7501，以及 agent 进程直接上报的 hooks，后者是工具、提问和回复的主要来源。

两类控制接口

业务动词（读写 pane、建删 worktree、卡片、提议、等待）由 core 提供，客户端全部关闭也可使用；界面动词（分屏、聚焦、缩放、布局）只有画界面的一方能做，留在客户端。agent 与 First Mate 的 seahelm 命令行按这一划分路由。

First Mate 回路

First Mate 由 core 在 seahelmd 中启动，它的命令行调用回到 core，先过权限闸门再执行：auto 直接执行，ask 变成审批卡由用户在任一入口回答，deny 拒绝。这是唯一一条会话反向控制核心的路径，权限边界在此。

core 与 gateway 的边界

core 管“事实是什么、能做什么”：对谁问都给同一个答案，只信任本机 socket（0600），不碰网络。gateway 管“谁在问、怎么跟他说话”：唯一面向网络的组件，负责身份、传输与渠道呈现；对 core 来说它只是又一个客户端，只用公开接口——core.sock 上的业务调用与事件订阅、message.subscribe、cards.changed，以及直连 seahelmd 的终端流。它不读 core 的文件，也不经过 App。

归 seahelm-core

  • Agent 状态、PR、用量
  • 卡片：生成、回答的执行、过期判定
  • 消息时间线
  • First Mate：会话、权限闸门、审批与提议、say
  • 通知决策：该不该提醒
  • pane / worktree 动作、等待
  • pane 的稳定编号 #n、文本命令的解析与执行

归 seahelm-gateway

  • 鉴权：配对码、token、Telegram initData 校验、allowed_users、Mini App 域名、分享链接
  • 连接：WebSocket、重连、每个客户端的重放序号
  • 终端转发：直连 seahelmd，不经 core
  • Telegram 适配：长轮询、格式转换、分段、媒体、限流
  • 通知路由：发到哪个聊天、默认聊天、静音
  • 渠道呈现：按钮与卡片 id 的映射、进度草稿、群组与私聊
  • 聊天绑定：哪个聊天在跟哪个 pane 说话
  • 渠道密钥：bot token、配对密钥，存在 gateway 自己的配置里
  1. 换一个渠道（Slack、邮件）也原样需要的，放 core；只与某个渠道的协议有关的，放 gateway。
  2. 持有外部世界的凭据或信任关系的，放 gateway。
  3. 所有入口必须看到一致结果的业务状态，放 core。

灰色地带的约定

  1. 命令语言（/go #3、/order、@worktree）：解析与执行在 core，接口为“文本 + 上下文（当前绑定的 pane）”；聊天与 pane 的绑定留在 gateway，调用时作为上下文传入。
  2. 在 Telegram 与 First Mate 对话：core 不知道聊天 id。gateway 调用 autopilot.say 时记下提问的聊天，订阅 First Mate 的消息流，在回合结束时把回复发回去。
  3. 非授权来源的消息（监控频道等）：识别与解析在 gateway，由此触发的动作走 core 业务接口，同样经过闸门。
  4. 谁回答了卡片：鉴权只在 gateway；调用带 _meta.via（如 telegram:@name），core 只记入审计，不据此授权。
  5. 配置与密钥：bot token、host_gateway、配对密钥迁入 gateway 自己的配置文件，不再与 App 设置混在 config.json。
