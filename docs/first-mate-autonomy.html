First Mate 自治设计：从看着你做，到替你做

刚装好的 First Mate 几乎什么都不会。它看你怎么处理 worktree、怎么回卡片、怎么跟 agent 说话，把规律写成"习惯"，攒够证据后再问你一句：以后这件事交给我？

01帮我处理杂活清理、建 worktree、拉任务、定时调研
02从我的操作中学习操作、卡片回答、对话，都是证据
03不过度打扰能合并就合并，能事后说就不先问

已定的决策

讨论中你拍板的十条。后面每一节都按它们展开。

#决策
D1放宽必须你点一次头，收紧自动。由 core 强制，提示词说了不算。
D2先解决 worktree 堆积，也用它把学习闭环完整走通。
D3First Mate 从几乎一无所知开始，从你的操作和会话中学，逐步自动化。
D4内置规则（fix-ci、cleanup-merged、triage-issues）保留，作为通用规则；学到的习惯是你个人的，与之并列。
D5可以从你跟各 pane 里 agent 的对话中学习，接受这些内容会发给模型 API。
D6首次开启时发一张"盘点"卡，作为冷启动，这是唯一一次主动打扰。
D7学到的一切都只放本机：习惯、项目记忆都不进仓库。
D8简报不定时，First Mate 学你什么时候、在哪儿看，自己决定发送时机。
D9阈值它自己调，但不超出 core 设定的硬边界。
D10能确定项目的链接（GitHub issue/PR，以后加上已映射的 Jira key）等同于你点了项目名，直接开工，不发卡。

原理：学习闭环

三个角色，各做各最擅长的事。core 是确定性代码，负责记账和把关。First Mate 是 LLM，负责看出规律。你负责每一次放宽。

一条习惯只有在触发条件能用 core 实测的事实表达时，才有资格升到"自动"。 "PR 已合并、全部推送、闲置 3 天"测得出来，可以自动。"跟项目目标无关了"测不出来，最多到"问你"。First Mate 声称"我很确定"不算数。

为什么这样分工

记录和执行放在 core

证据要准，不能靠模型回忆。自动执行要由代码把关：模型可能被 issue 正文里的一句话带偏，可能说"记住了"却没调用工具，也可能在长会话里忘掉规则。core 不会。

归纳放在 First Mate

"这 7 次删除其实是同一种情况"、"他说'文档 PR 别管'是一条规则"，这类提炼只有模型做得了。所以它只负责提议，提议要经 core 校验、由你批准，才会生效。

习惯怎么长大

每条习惯有四个档位。往上走一档要证据加你的同意，往下走一档是自动的。下面是一个可以操作的模拟，用"删除已合并且干净的 worktree"这条习惯来演示。

observe只计数，什么都不做
suggest简报里提一句，不发卡
ask一键确认后执行
auto直接做，事后汇报
门槛：同类操作 3 次，跨 2 天、2 个不同 worktree，才进 suggest；连续批准 5 次才会问你要不要转自动。

升档卡每个档位只发一次。你说"先不要"，它就重新攒证据，攒够之前不再问。被拒绝、被你撤销，或者卡片连续两次没人理，都会自动降一档，不用问你。

习惯长什么样

按项目存在本机，~/.config/seahelm/first-mate/habits/<repo>.yml，你能看、能改、能删。每条都带出处，所以永远能回答"你凭什么这么做"。

- id: delete-merged-clean
  about: worktree.cleanup
  when: { pr: merged, days_since_merge: ">=1", uncommitted: 0, untracked: 0,
          ignored_files: 0, unpushed: 0, busy_panes: 0 }
  do: delete_worktree
  level: ask            # observe | suggest | ask | auto
  status: active        # 偏好变了：原地标记 superseded，新旧并排保留
  observed: 2026-11-05
  sources: [obs-0012, obs-0031, obs-0040]   # 指回观察记录
  origin: inventory     # general | inventory | learned | user
  evidence: { approved: 5, rejected: 0, manual: 3, ignored: 0 }
  examples: [feat/island-pill, fix/web-question-details]

习惯分两种。可测习惯的条件只用 core 的事实词汇，由 core 自己匹配，最高能到 auto。判断习惯的条件是一句话，比如"只改了文档的 PR"，由 First Mate 判断是否适用，core 把它封顶在 ask。

和现有规则的关系

  • 仓库里的 .seahelm/automations.yml 是人写的、共享的，它给该仓库所有习惯封顶：那里写了 deny，习惯就算到了 auto 也不执行。
  • 你批准过的习惯，在它的条件范围内取代你的全局默认值（autopilot_autonomy）。否则 delete_worktree: ask 这个默认值会让任何学来的 auto 都永远动不了。
  • 内置规则照常工作（D4）。cleanup-merged 仍然在 PR 合并时触发，习惯在此之外补上每日清扫和学来的阈值。

可测事实：core 看得到什么

自动化全靠这张词汇表。今天的 facts.rs 有两个漏洞，第一期就要补：

  • 看不到被 ignore 的文件。git worktree remove 会悄悄删掉 .env、本地笔记、数据文件，卡片上一个字都不提。
  • squash 合并后误报"未推送"。仓库在合并后删掉远端分支，分支上的提交就不在任何远端引用上了。其实 GitHub 还保留着 refs/pull/N/head，但现在的 PR 拉取不带 head oid，没法比对。
事实怎么测
prmerged / closed / open / draft / none，来自 core 的 PR 拉取
days_since_mergePR 的 mergedAt
uncommitted · untrackedgit status --porcelain（同今天）
ignored_filesgit status --ignored，减去可重建的目录（node_modules、target、.build、DerivedData、dist、.venv…），剩下的文件名直接写在卡片上
unpushedHEAD 上既不在任何远端引用、也不在 PR head 下的提交
idle_days最后一次提交、pane 状态变化、你在该 worktree 里发 prompt，三者取最晚
busy_panes同今天
identical_to_basegit merge-tree 合并进 base 不产生任何改动

试一试：这个 worktree 会怎么处理？

假设你已经把"已合并且干净"批准到了 auto。改下面的条件，看 First Mate 走哪条路。

首期：worktree 清理

今天的清理只在"看到 PR 合并"这一刻触发一次。First Mate 关着时合并的、PR 被关掉的、做到一半放弃的，都会永远留着。新设计分四步：

1 · 补全事实

上面那张词汇表，出现在每一张删除卡上。光这一步就能让现有的卡片说实话。

2 · 每日清扫

每天一次（First Mate 开启时也扫一次），core 测量每个活着的 worktree 并匹配习惯：auto 的直接删并汇报，ask 的进简报里那张批量卡，suggest 的列一下，其余不动。

3 · 盘点卡（冷启动）

worktree 会堆起来，恰恰因为你不删，First Mate 也就没机会学。所以首次开启时，按事实分组发一张卡，你对每组选一次，就是第一批训练数据。

4 · 持续学习

之后谁删了 worktree、你怎么回卡，都记成观察。core 用删除前最后一次测量当证据，app 那边几乎不用改。

盘点卡：长这样，可以点

FIRST MATE · 盘点 · 24 个 WORKTREE
我按实际状态分了组。每组选一次，我就照着学。
你的选择会生成这些习惯：

    
一组选择不管覆盖几个 worktree，都只算一次决定。"有未推送工作"这组只能选留或问，永远不会被学成自动删。

  




安全底线：只要未提交、未跟踪、被 ignore 的非缓存文件、未推送提交中有一项大于零，这个 worktree 就不可能被任何 auto 习惯匹配。
core 根本不接受这样的 auto 条件，攒多少证据都不行。主仓库和集成仓库永远不匹配。删除时保留分支（同今天）。

这些阈值只决定什么时候问你，不决定什么时候动手。所以让它自己调，不会绕开 D1。core 守住边界，每次调整都写审计日志，并在简报里说一句。

项目记忆


每个项目一份，放本机（D7）：目标、当前里程碑、优先级、禁区、完成标准，再加上学来的笔记，比如"提交前先跑测试"、"PR 总结用中文"。



  
来源
你对 First Mate 说"记住……"；复盘时读你反复对 agent 说的话（D5）。只从你本人的操作和话语中学。agent 的输出、issue 正文、网页、邮件只当作数据，永远不会变成指令。

  
让每个 agent 都看到，又不进仓库
core 本来就会在每个 seahelm pane 里 agent 的 SessionStart 时注入 suggest 引导（core-hooks/src/suggest.rs）。项目记忆一起附上，Claude、Codex、Cursor 启动就带着它。有长度上限（约 2000 字符），附带占用比例，逼 First Mate 主动精简。

未来：邮箱和日历


日历让作息学习更准：开会时不发卡，简报在会议间隙发。邮件是又一个任务来源，跟 GitHub、Jira 并列，只进简报。规则借鉴 OpenClaw：只读连接；邮件交给隔离的读取器，产出的摘要标记为不可信；这两类来源都不会变成习惯或指令；每个来源可以单独开关。
