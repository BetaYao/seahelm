# OSC 7501（Program Status Protocol）接入方案

状态：提案，探针已完成（见第 6 节），尚未改 Ghostty / Seahelm 代码。

规范：<https://www.superlogical.com/rex/docs/build/program-status>（rev 0.4，2026-10-10）。
背景：<https://mitchellh.com/writing/program-status-osc7501>。libghostty 实现：ghostty-org/ghostty#14560（2026-10-06 合并）。

## 1. 为什么做

程序自己通过 pty 告诉终端它在干什么：`idle` / `working` / `done` / `blocked` / `error`，外加原因。比扫屏幕可靠，比 hooks 通用——任何程序（包括 terraform、brew 这类普通 CLI）都能报，不需要每个工具一个 shim，SSH 和容器里也照样能用。

Claude Code 2.1.300 已经内置：启动时发 `OSC 7501 ; ?` 探测，**只有终端回应了才上报**（二进制里有 `probe: no reply to OSC 7501 ; ?` 和 `answer("programStatus", …)`）。Seahelm 现在不回探测，所以它一个字节都不发。

## 2. 规范要点

- 上报：`OSC 7501 ; key=val:key=val ST`，ST 是 `ESC \` 或 BEL。值字符集 `A-Za-z0-9_.,+/=-`，无需转义。整条 ≤ 4096 字节；超限、base64 非法、解码后含控制字符 → 整条丢弃。未知键忽略，重复键后者生效。
- 键：
  - `state`（必填，未知值整条忽略）：`idle` `working` `done` `blocked` `error`，以及 `clear`（不是状态，是删除）
  - `kind`：`permission` / `question` / `auth`，仅 `blocked` 有意义
  - `progress`：0–100，仅 `working` / `blocked`；缺省或非法 = 不确定
  - `app`：稳定程序标识（≤32），从最近的祖先继承；不是展示名
  - `title`（≤192 解码后）、`msg`（≤2048 解码后）：base64 UTF-8，单行
  - `id`：`/` 分隔的段，每段 1–32 字符，最多 8 级、总长 128；缺省 = root 记录
- 记录：每个 id 一条，每次上报**整条替换**（没带的键丢掉）。`clear` 删除该记录及其子树；不带 id 的 `clear` 删全部。记录属于终端而非屏幕（切 alt screen 不影响），RIS 清空，DECSTR 不清。每终端最多 256 条（至少支持 64），满了淘汰最久未更新的。
- 生命周期（无心跳，由终端维护）：
  - `working` / `blocked`：进程退出或下一个 prompt（OSC 133 `A`）时删除
  - `done` / `error`：跨进程退出和 prompt 保留，直到用户看过
  - `idle`：替换或清除前一直有效，进程退出/prompt 时**可以**删
- 探测：程序发 `OSC 7501 ; ? ST`，支持的终端回 `OSC 7501 ; ? [: states=… : kinds=…] ST`（没列就是默认的五个状态和三个 kind）。程序可以紧跟 `CSI c`，先收到 DA1 回复 = 不支持。探测是可选的，程序也可以不探测直接发。
- 安全：内容全部不可信；msg/title 不当标记解释，展示前去掉 bidi 覆盖和不可见格式字符；由它触发的通知、声音要限流；终端唯一的回写是探测回复，记录不可读。

## 4. 实施步骤

### 4.1 Ghostty 补丁（已完成）

实际做法和最初设想不同：**不升级子模块**，仍锁在 `12967b68f`，在它上面打一个本地补丁。上游 #14560 / #14630 直接 cherry-pick 有 29 处冲突（中间上游加了 `kitty_desktop_notification`、`unknown` 等 OSC），而且大半是 GhosttyKit 用不到的 libghostty-vt C API；跨两个月升级的风险也不值得为这一个功能承担。

- 补丁：`scripts/ghostty-patches/0001-osc7501-program-status.patch`。改补丁的流程：在 `ghostty/` 里切到本地分支 `seahelm/osc7501`（不推远端），改完提交，`git format-patch -1 --zero-commit -N` 覆盖补丁文件，再把子模块切回锁定的 commit
- `setup.sh`：有补丁时在临时 worktree 里 `git apply` 后构建，子模块 checkout 保持干净；缓存目录是 `~/.cache/seahelm/ghosttykit/<sha>-<补丁hash>`，Ghostty 资源（`zig-out/share`）一起缓存。CI（`release.yml`、`warm-ghostty-cache.yml`）的缓存 key 同样带上补丁 hash
- 补丁内容：
  - 原样移植上游 rev 0.4 的解析器 `src/terminal/osc/parsers/program_status.zig` 和它依赖的 `osc/kitty_metadata.zig`；`osc.zig` 接上 `7501` 状态机，`Parser.nextSlice` 补了一个简单版本供解析器测试使用
  - `stream.zig` 新增 `program_status` action；libghostty-vt 的 `stream_terminal.zig` 忽略它（不移植 vt C API）
  - `termio/stream_handler.zig`：回应探测（`OSC 7501 ; ?` → `query_reply`，沿用请求的终止符）；上报复制成 surface message；RIS 时发一次全量 `clear`
  - `Surface.zig` 解码后调用新的 apprt action `GHOSTTY_ACTION_PROGRAM_STATUS`，**追加在枚举末尾**，Seahelm 已用的 action 序号不变
  - `ghostty.h`：`ghostty_action_program_status_s { state, kind(int8, -1=无), progress(int8, -1=无/不确定), text* }`，`text` 指向 `{ id, app, title, msg }`（以 0 结尾，空串=没发，仅在回调期间有效）。字符串放在指针后面，是因为 `ghostty_action_u` 被编译期断言固定在 24 字节
- 与原计划的偏差：**探测无条件回应**，没有做 config 开关。这个构建只服务于会消费上报的 Seahelm；如果要提给上游，再加开关
- 验证：`zig build test -Dtest-filter=7501` 88/88，`-Dtest-filter=osc` 353 通过 1 跳过，`Action.Key` 与 `ghostty.h` 一致性测试通过

### 4.2 Seahelm：记录存储

`Sources/Status/ProgramStatus.swift`，纯逻辑、可单测：

- `ProgramStatusRecord` + 每个 Station 一个 `ProgramStatusStore`：按 id 存、整条替换、`clear` 删子树、全量 clear（RIS 时 Ghostty 会报一次）、256 上限按最久未更新淘汰、`app` 沿祖先继承
- 生命周期：OSC 133 `A` 和进程退出时删 `working` / `blocked`；`done` / `error` 保留，用户聚焦该 pane 视为已读

### 4.3 Seahelm：接入状态管线

- `ProgramStatusDecoder: SignalDecoder`，新增 `EventSource.osc7501`
- 优先级：与 hooks 同级，高于 OSC 133 和文本匹配
- 映射（只看 root 记录）：

  | 7501 | AgentStatus | 附带 |
  |---|---|---|
  | `working` | `.running` | `progress` 进 `PaneProgressBar` |
  | `blocked` | `.waiting` | `kind` + `msg` 作为原因，上卡片 / Island |
  | `idle` | `.idle` | |
  | `done` | `.idle` | 未读标记 |
  | `error` | `.error` | `msg` |

- 子记录（层级 id）先只在 pane 详情里列出，不参与 rollup
- 规范要求：收到第一条 7501 后，停止把 OSC 9;4 映射成 root 记录（会抹掉 `kind` 和 `msg`）
- `seahelm pane explain` 输出里带上当前 7501 记录，方便诊断

### 4.4 安全

msg / title 展示前去掉 bidi 覆盖和不可见字符；7501 触发的通知按 pane 限流。

## 5. 风险：zmx 在中间

- **attached 会话**：OSC 9;4 今天能透传，上报方向应该没问题。探测回复要经 zmx client 的 stdin 回到 pty，需要实测。
- **detached 会话**（`SessionManager.createDetachedSession`）：**已实测确认**（6.2）——没有 client 回探测，Claude 判定不支持，之后 attach 上去也**一条都不发**。和 OSC 10/11 被吞是同一个问题。这是最大的缺口，可选的补法：
  1. 给 zmx 打补丁或提需求：无 client 时由 daemon 自己回 `OSC 7501 ; ?`（zmx 本身就用 libghostty-vt，开 `GHOSTTY_TERMINAL_OPT_PROGRAM_STATUS` 即可回）。要注意 attached 时 daemon 和 client 都回会产生重复回复——程序端忽略第二个即可，但需要验证
  2. detached 创建时先挂一个隐藏的 attach client（`zmx-attach.py` 那样），等 agent 探测完再断开
  3. 向 Claude Code 要一个跳过探测、强制上报的环境变量（2.1.300 里没有）
- **Seahelm 重启后重新 attach**：记录只在 Seahelm 内存里，丢失。没有心跳，长时间 `working` 要等下一次状态变化才恢复；在那之前 hooks 和扫屏继续兜底。
- 因此 7501 是**新增一层**，不替代 hooks——hooks 还承载 cwd、工具事件、question 等 7501 不覆盖的信息。

## 6. 探针（第一步）

在改 Ghostty 之前先确认：

1. Claude Code 实际发出什么：`app` 名、是否用子 id、`blocked` 是否带 `kind`、`done` / `idle` 的时机
2. 探测回复在 zmx 后面能否往返

做法：一个 Python pty 测试架子 `scripts/probe/osc7501_probe.py`，扮演终端回应探测（7501、DA1 等），记录所有 OSC 7501 序列；分别直接跑 `claude` 和经 `zmx attach` 跑。

脚本：`scripts/probe/osc7501_probe.py`。跑法（在一个非 git 的空目录里，`--setting-sources local` 绕开用户的 hooks 和 bypass 权限模式，脚本会清掉 `SEAHELM_*` / `ZMX_*` / `CLAUDE*` 环境变量，避免上报到正在运行的 Seahelm 或当前 Claude 会话）：

```bash
python3 -I scripts/probe/osc7501_probe.py -- claude --model haiku --setting-sources local --permission-mode default
python3 -I scripts/probe/osc7501_probe.py --no-reply -- claude …            # 基线
python3 -I scripts/probe/osc7501_probe.py --zmx probe --zmx-bin <bundle>/Contents/Resources/bin/zmx -- claude …
```

脚本流程：等启动 → 输入「用 Bash 跑 `touch osc7501-probe.txt`」→ 批准权限 → 等这一轮结束 → 两次 ctrl-c 退出。

### 6.1 结果（Claude Code 2.1.300，2026-10-15）

| 场景 | 7501 上报 |
|---|---|
| 直接 pty，回应探测 | `idle` → `working` → `blocked` → `working` → `done` |
| 直接 pty，**不**回应探测 | 0 条 |
| 经 `zmx attach`（0.8.1），回应探测 | 和直接 pty 完全一致，探测和回复都能穿过 zmx |
| `zmx run` detached 创建，之后 attach | **0 条**，attach 后客户端也没收到探测 |

实际序列（直接 pty 和经 zmx attach 一致）：

```
 1.3s  state=idle:app=claude-code                     ← 收到探测回复后立刻发
 7.4s  state=working:app=claude-code                  ← 提交 prompt
20.4s  state=blocked:app=claude-code:kind=permission:msg=approve Bash: touch osc7501-probe.txt
22.7s  state=working:app=claude-code                  ← 批准
26.0s  state=done:app=claude-code                     ← 这一轮结束
```

### 6.2 观察

- `app` 恒为 `claude-code`，每条都带；只用 root 记录，这次没有出现 `id`、`progress`、`title`
- 只有 `blocked` 带 `msg`，内容就是权限请求本身，直接可以作为 Island 上的待办文案
- 一轮结束发的是 `done`，不是 `idle`；只读命令（`echo`）不经过 `blocked`
- ctrl-c 退出时没有发 `idle` 或 `clear`，`done` 会一直留着——符合规范（`done` 跨进程退出保留），Seahelm 需要按规范在用户看过后清掉
- 启动时 Claude 依次发 7501 探测、XTVERSION、kitty 键盘、DECRQM、DA1；DA1 用作超时兜底
- 二进制里有 `state=clear:id=…` 的拼装，说明某些场景（可能是 subagent 或后台任务）会用子 id，这次没覆盖到；`kind=question` / `auth` 也没测
- 二进制里没有跳过探测、强制上报的环境变量

### 6.3 对方案的影响

- 映射表（4.3）可以照用；`done` 要单独做「未读」状态，不能直接当 `idle`
- `blocked` 的 `msg` 能补上 hooks 之外的权限请求来源，不依赖 `PermissionRequest` hook
- detached 缺口要在 4.1 之外单独解决（见第 5 节的三个补法），否则 FirstMate、`seahelm pane run` 这类后台起的 agent 拿不到 7501
