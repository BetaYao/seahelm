# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Seahelm (sea + helm) is a native macOS terminal multiplexer built with Swift + AppKit. It integrates the Ghostty terminal engine (via C bindings through GhosttyKit.xcframework) to render terminals, keeps each pane alive in a session daemon of its own (seahelmd, Rust, in `seahelmd/`), and provides a dashboard UI for browsing git worktrees with agent status detection.

## Build Commands

```bash
# First-time setup: init the Ghostty submodule + build/reuse GhosttyKit.xcframework
scripts/setup.sh

# Build into .build/, kill any running Seahelm, and launch the debug app
./run.sh                 # add --clean-restart to wipe .build first

# Run UI tests (regenerates the project, optionally filtered to one class)
./run_ui_tests.sh [TestClass]
```

Note: `run.sh` builds with `-derivedDataPath .build`, so the live app runs out of `.build/`, NOT the default `~/Library/Developer/Xcode/DerivedData` bundle a bare `xcodebuild` or Xcode.app run would produce — when inspecting a running instance, use the bundle the live pid actually came from.

```bash
# Generate Xcode project from project.yml (requires xcodegen)
xcodegen generate

# Build
# NOTE: CodeEditSourceEditor pulls in the SwiftLint build-tool plugin, which
# requires trust validation. Headless/CLI builds must pass -skipPackagePluginValidation
# (in Xcode.app, click "Trust & Enable" once instead).
xcodebuild -project seahelm.xcodeproj -scheme seahelm -configuration Debug -skipPackagePluginValidation -skipMacroValidation build

# Run tests
xcodebuild -project seahelm.xcodeproj -scheme seahelmTests -configuration Debug test

# Run a single test class
xcodebuild -project seahelm.xcodeproj -scheme seahelmTests -configuration Debug test -only-testing:seahelmTests/ConfigTests

# Run a single test method
xcodebuild -project seahelm.xcodeproj -scheme seahelmTests -configuration Debug test -only-testing:seahelmTests/ConfigTests/testDefaultConfig

# Run UI tests — prefer targeted unit classes during active development.
# The full seahelmUITests suite is slow AND hijacks the live app's control
# socket, freezing panes at "running". Avoid it unless you specifically need it.
xcodebuild -project seahelm.xcodeproj -scheme seahelmUITests -configuration Debug test

# Clean build
xcodebuild -project seahelm.xcodeproj -scheme seahelm clean
```

The project uses XcodeGen (`project.yml`) to generate the Xcode project file. After modifying `project.yml`, regenerate with `xcodegen generate`.

**Helper scripts:** `scripts/build-seahelmd.sh <dest>` builds the session daemon (`seahelmd/`, Rust) for the arch being built and installs it — the app's "Embed and sign seahelmd" phase runs it, so a build needs cargo, and on first build zig 0.16 and network (libghostty-vt is built once per Ghostty commit and arch into `~/.cache/seahelm/libghostty-vt`). `scripts/disk-drop-recover.sh` recovers from the workspace volume dropping out, which can wedge the session daemons (`seahelmd list` answers `status=unreachable` and remounting does not heal them): it captures each pane's `claude --resume` id, kills the app and every seahelmd process, clears the stale sockets, and relaunches the bundle — `--check` diagnoses only (exit 10 = wedged), `--kill-strays` also reaps other processes spinning on a dead cwd.

## Architecture

**Four-layer design:**

1. **App Coordinators** (`Sources/App/`)
   - `MainWindowController` — Window owner, embeds content VCs, positions traffic lights, handles keyboard shortcuts via `SeahelmWindow` subclass
   - `TabCoordinator` — Orchestrates tab switching, repo VC lifecycle (cached in `repoVCs[repoPath]`), status update forwarding, and session state save/restore
   - `TerminalCoordinator` — Split pane operations (split, close, move focus, resize), worktree deletion, surface manager ownership
   - `PanelCoordinator` — Manages side panels (AI panel, notification panel)

2. **UI Layer** (`Sources/UI/`)
   - `Dashboard/` — One layout, left/right (`setupLeftRightLayout`, accessibility id `dashboard.layout.left-right`): the fleet overview on one side as navigator, a `FocusPanelView` hosting the selected terminal on the other. `DashboardOverviewView` is that overview — every worktree a row, grouped by `WorktreeGroupingMode` (repository, status, activity time, or `pane`, which expands to a third level of pane rows). Edit mode swaps in `EditLayoutContainerView`: a terminal column and a file-preview column, each with an `EditTabStripView`, split by a draggable divider. The former Grid / TopSmall / TopLarge modes and the mini-card sidebar are gone; the "grid-aware" wording left in `DashboardFocusController` is a remnant, not a feature.
   - `Repo/` — `RepoViewController` with `SidebarViewController` for worktree switching; `SplitContainerView` hosts split panes
   - `Split/` — `SplitContainerView` renders `SplitTree` as frame-based leaf views with `DividerView` drag handles and dim overlays on unfocused panes
   - `Chrome/` — Two-column `WindowChromeController` (sidebar/terminal headers, divider, collapse)
   - `Dialog/` — Quick switcher (Cmd+P) and new branch dialog (Cmd+N)
   - `SidePanel/` — Per-worktree side panel with Files / Changes tabs (`WorktreeSidePanelViewController`). Changes answers "what here still has to go in a PR": uncommitted work, then committed work the base lacks. A squash merge leaves git no ancestry to go on, so committed work is counted from the last merged PR's head when GitHub has one (`MergedPRLookup`), otherwise as what `git merge-tree` says merging into the base would change (`GitDiff.branchChangedFiles`). The old First Mate orders tab (`BridgePanelViewController`) and the inline command composer (`InlineWorktreeCreateView`) are gone: pending orders and the command line both live in `Island/`.
   - `Diff/` — Code-review diff viewer (`DiffReviewView` + `DiffSyntaxHighlighter`)
   - `Helm/` — `GrowingTextView` (extracted from the former `CommandInputView`), the keyboard-help overlay and the shortcut hint bar. The command line itself is the Island's (`Island/OpenedSurfaceView`, `/ @ #` autocomplete); the sidebar has no composer.
   - `StatusBar/` — Fixed 26pt bottom bar: mode indicator, global Claude/Codex usage, notification summary, shortcuts
   - `Island/` — Floating "dynamic island" panel (morphs closed pill ↔ open surface) for notifications/status
   - `Settings/` — Tabbed settings window (`WizardKit` holds the controls the Telegram setup wizard is built from). There is no first-run wizard: a fresh config opens on the main window with the default agent picked from PATH (`AgentDetector`), and an empty fleet shows a single "Add project" row with nothing on the terminal side.

3. **Core Services** (`Sources/Core/`, `Sources/Status/`)
   - `AgentRegistry` — Single source of truth for all agent state; delegates notify UI of changes
   - `StatusPublisher` — Timer-based polling (2s) on background queue, reads viewport text via `ghosttyLock`-protected C API calls
   - `StatusDetector` — Authoritative status detector. Priority: process exit > OSC 133 shell phase > text pattern matching > Unknown — though nothing feeds the OSC 133 tier (`shellInfo` is always nil), so in practice it is process exit > text. Its text-pattern tier consults a `CompiledManifest` from the manifest engine (see below); the manifest layer augments, it does not replace, this ladder.
   - `WorktreeStatusAggregator` — Aggregates per-pane statuses into per-worktree status, fires `WorktreeStatusDelegate`
   - `Config` — JSON config at `~/.config/seahelm/config.json`; uses `decodeIfPresent()` for backward compat (migrated from legacy ~/.config/amux on first launch)
   - `StationRegistry` — Global registry mapping surface IDs to `Station` instances
   - `ExternalChannel` — Protocol for inbound remote-control chat. `TelegramChannel` is the live one: a Bot API bridge (`TelegramBotAPI`, blocking calls) that long-polls `getUpdates` on a thread of its own and answers with `sendMessage`. Its transport is the system libcurl in-process (`CurlClient`, linked as `libcurl.tbd`, variadic setopt wrapped in `SeahelmCurl.h`), not URLSession: in this process URLSession requests to Telegram hung after the first one or two (no response, no error, timeouts not firing) while the same requests from curl never failed. It was `/usr/bin/curl` in a child process until that was measured at a fresh TCP+TLS handshake per call (≈1.7s, so 2–3s per chat reply); `CurlClient` pools easy handles so connections are reused (≈0.5s). Cancellation is the xferinfo callback, so `invalidate()` takes up to a second. No permissions and no local app, but it needs a bot token from @BotFather (`TelegramConfig.botToken`, kept in config.json beside the pairing secret). `TelegramConfig.allowedUsers` (numeric ids or `@usernames`) is a hard gate — empty obeys nobody — and it also decides what a message *is*: from an allowed user it is an order (in a private chat any text; in a group a `/command`, a line starting `@thebot`, or a reply to one of the bot's messages — bare prose in a shared group must not steer an agent); from anyone else it is rule input for `TelegramRuleEngine` (a monitoring channel the bot sits in, a colleague in a group). There is no echo guard because a bot's own messages never come back as updates. **There is no forum-topic support, on purpose**: a conversation is a chat id, full stop. Messages are not threaded (`message_thread_id` is neither decoded nor sent), so in a forum group a command said inside any topic is answered in General; seahelm opens no topics of its own (the old `auto_topics`/`topic_chats` config and `/home` verb are gone, and their keys are ignored if still in config.json). `CommandSessionStore` drops any leftover `telegram:<chat>#<thread>` session at load. Pane notices carry the pane's `#n` on their second line (`MainWindowController.noticeText`), since a fleet-wide chat hears many panes and the handle is what `/go`/`/order` take. Media is downloaded only for messages from allowed users. A chat bound to a pane that is no longer in the fleet sends nothing (it does not fall to a neighbour in the worktree). Command replies' `CommandButton`s become inline buttons through `ChatCallbackRegistry.buttons(for:)`. Live progress (`ChatProgressReporter`) differs by chat type: a **group** gets one edited message per bound pane, deleted when the turn ends; a **private chat** gets a board streamed with `sendMessageDraft` — the bound pane in full plus a line per other running/waiting pane, with Telegram's Stop button (→ `stopped_message_generation` → `MainWindowController.stopBoundPane` sends Esc). Measured constraints that shaped it: drafts are private-chat only (`TEXTDRAFT_PEER_INVALID` in groups), one per chat (a second `draft_id` replaces the first), fade ~12s after the last call (docs say 30) and on any bot message, so the board is re-sent every 8s while anything runs; the Stop update is dropped unless `allowed_updates` asks for it, and its `draft_id` arrives as a string. The bot's **Mini App** (BotFather ▸ Configure Mini App, plus the `setChatMenuButton` menu button) is seahelm-web at `tg.seahelm.dev`: the same cloudflared tunnel to the Host Gateway as `gw.seahelm.dev`, but deliberately *not* behind Cloudflare Access — Access's login page sends `X-Frame-Options: DENY`, and Telegram desktop/Web frames Mini Apps. The gateway compensates: it records each upgrade's Host (keyed by the internal hop's port) and, on the Mini App host — `host_gateway.telegram_host` if set, else the host of `telegram.mini_app_url` (Settings ▸ Telegram ▸ Mini App, which also points the bot's menu button at it on every bridge connect) — refuses the pairing code; there a client signs in only with Telegram launch data (`tgWebAppData` in the URL fragment, verified by `TelegramInitData` — HMAC over every field but `hash`, `signature` included — and the user on `allowed_users`) or a token already issued. Outbound goes through `TelegramFormatter`: the bridge's light markdown to Telegram HTML, chunked to 4096, resent flat if Telegram returns 400.

4. **Terminal & System** (`Sources/Terminal/`, `Sources/Git/`)
   - `GhosttyBridge` — Singleton wrapping the Ghostty C API (`ghostty.h` via bridging header)
   - `Station` — Wraps `GhosttyNSView` (NSView + Metal renderer + PTY); manages surface lifecycle, reparenting, and backend session attachment
   - `SplitTree` / `SplitNode` — Tree data structure for split pane layout; serializable for persistence in config
   - `WorktreeDiscovery` — Runs `git worktree list --porcelain` to discover worktrees

## Key Patterns

**Surface lifecycle:** Station instances are long-lived — created once per split leaf, reparented between views (dashboard focus panel, repo tab split containers). `reparent(to:)` uses `CATransaction` to suppress animations, then defers size sync and focus restoration via two `DispatchQueue.main.async` passes. Surfaces are destroyed only on explicit deletion or app quit.

**Tab switching:** `detachActiveTerminal()` removes the active `SplitContainerView` from its superview before embedding the new tab's content. This prevents Z-order conflicts when surfaces are shared across views.

**Split pane system:** `SplitTree` is a binary tree of `SplitNode` (leaf or split with axis + ratio). `SplitContainerView.layoutTree()` computes frame-based positions for each leaf, places `GhosttyNSView` instances, adds `DividerView` drag handles, and updates dim overlays. Focus is tracked via `tree.focusedId`; `GhosttyNSView.onFocusAcquired` callback keeps the tree in sync when user clicks a pane.

**File drop:** dragging files (or an image out of a browser, Photos, Mail) onto a pane types their paths into *that* pane. `SplitContainerView` is the drag destination, not each `GhosttyNSView`: a `DividerView`'s 16pt hit strip overlaps the pane edges, and the container already knows every leaf frame. `draggingUpdated` resolves the pane under the cursor (`dropTargetStationId(at:paneFrames:)`; the seam goes to the nearest pane) and lights it with `GhosttyNSView.setDropHighlight`, an in-view sublayer like the inactive wash. Asleep panes, and panes covered by the preview overlay, refuse. `TerminalDrop.resolveText` takes the first of: file URLs → backslash-escaped paths (`ShellEscape.backslash`, native Ghostty's escaping) plus a trailing space; file promises → received into `$TMPDIR/seahelm-drops/<uuid>/`; bare image data → a PNG there; otherwise the dropped text verbatim. The text goes in through `Station.sendText` — `ghostty_surface_text`, the paste path, so bracketed paste applies and agent TUIs read a pasted image path as an image — and the drop focuses that pane and activates the app. In a pane whose agent is Claude Code (`AgentRegistry.pane(for:)`), dropped *images* attach instead of being typed (`AgentImagePaste`): each goes onto the general clipboard as PNG and the pane gets a real ctrl+v key event — Claude Code's `chat:imagePaste`, which reads the clipboard through `osascript … «class PNGf»` — then the user's clipboard is restored unless they copied in the meantime. It must be a key event, not `sendText`: inside a bracketed paste ctrl+v is just a pasted byte. Other files in the same drop follow as paths.

**Terminal palette follows the app theme, live:** dark everywhere or light everywhere. `terminal_theme_mode` (`app` default / `dark` / `light`, `TerminalThemeMode`) resolves into `GhosttyBridge.terminalIsDark`; `app` tracks `NSApp.effectiveAppearance` — the theme toggle calls `refreshColorScheme`, and a KVO observer catches macOS switching on its own under `theme_mode = system`. When the resolved palette moves, `refreshColorScheme` rewrites the single `theme =` override (`writeTerminalThemeOverride`; one theme rather than `light:…,dark:…` so the pins work), hard-reloads the config (Ghostty's `updateConfig` fans `change_config` to every surface), sets every surface's color scheme (DEC 2031 reports) and posts `.ghosttyColorSchemeDidChange` so terminal chrome and the empty-state helm (`HelmWatermarkView`) restyle. **Known cost:** Codex asks over `OSC 10;?`/`OSC 11;?` once at startup, caches the answer for the life of the process and does not enable DEC 2031, so a flip under a running Codex leaves it painting from the stale reading — it only sets a *background* and leaves text at SGR 39, so a stale Latte reading gives a `#e5e7eb` user-message pill under Mocha's `#cdd6f4` text (`#e5e7eb` pill + `#393947` composer in one frame is the fingerprint). Restart the agent, or pin `terminal_theme_mode`. From b28f441 the palette was latched per run to avoid this; it was reverted because a window whose panes disagree with it was the worse trade. Separately, a session with no pane attached is answered by the daemon itself: seahelmd's grid stands in for the terminal with the palette current when the session was created (`SEAHELMD_FACTS`, `SeahelmdLocator.sessionEnvironment`), so an agent asking OSC 10/11 before its pane arrives still reads real colours.

**Terminal persistence:** every pane's terminal lives in a **seahelmd** daemon — one process per session, built from `seahelmd/` and bundled as `Contents/Resources/bin/seahelmd` (`SeahelmdLocator`; verbs: `attach`, `run`, `new`, `send`, `history`, `kill`, `list`). The daemon owns the PTY and keeps the screen in libghostty-vt (`keep-vt`, from ttwwnn/keep), so a pane that attaches — the app relaunched, a web viewer — is repainted with both screens, history, modes and colours (`Terminal::handover`), and a slow client is repainted rather than queued without end. Sockets live in `/tmp/seahelmd-<uid>/<name>` (short: socket paths cap near 104 bytes). A pane runs `seahelmd attach <name>` (`Station.seahelmdAttachCommand`), which creates the session on the user's shell if it does not exist. An agent is launched as the session's own program, not typed into a shell: `seahelmd new --hold 10 <name> -- zsh -lic '<exports> && cd && clear && <agent>; exec zsh -l'` (`SessionManager.detachedLaunchCommands`) — the daemon holds it until the pane attaches, so it starts at the pane's size with the pane there to answer its startup queries, and nothing echoes. `runtimeBackend` is `"seahelmd"` or `"local"`; `MainWindowController` starts optimistically at `"seahelmd"` and falls back to `"local"` if the daemon is missing (`local` panes are plain processes with no persistence). Sessions are named `seahelm-<parent>-<name>` (`.` and `:` replaced with `_`, truncated past `maxSessionNameLength`) and created per split leaf; a health check runs 3s after creation (`Station.recoveryDelay`) and stale sessions trigger `recoverSeahelmdSession` (destroy + recreate). A session whose daemon is gone (a reboot) is recreated running the agent's resume command (`AgentSessionRef`). Split layouts are serialized to config for restore on relaunch.

**Pane follows its agent into a new worktree:** when an agent creates a worktree and starts working in it, that pane moves to the new worktree's card instead of the worktree standing up an empty pane beside it. The signal is the `cwd` **every** hook payload carries — not `CwdChanged` alone (it is installed, but it cannot carry the case below; `ClaudeHooksSetup.retiredHooks` retires `WorktreeCreate`, whose registration made Claude delegate worktree creation to us and broke `--worktree`). `WebhookStatusProvider.handleEvent` asks whether the cwd names a worktree it does not track: either it matches nothing, or — the case that used to be invisible — it sits *inside* a known worktree while being a worktree root itself, which is exactly where Claude Code's own `EnterWorktree` puts one (`<repo>/.claude/worktrees/<name>`). `matchWorktree` therefore takes the **longest** prefix, not the first. The detection is throttled per path and records a `PendingTransferTracker` entry keyed by canonical path plus the emitting `SEAHELM_PANE_ID`; when discovery integrates the worktree, `TabCoordinator.performPaneRehome` consumes it and moves **only that pane** (`StationManager.moveLeaf` → `SplitTree.removeLeaf`/`adopt`, keeping the Station and its seahelmd session), then `AgentRegistry.rehome` re-files the `PaneInfo` **without** unregister+register — which would reset the running agent's status, hook timers and event log. A worktree the pane arrives at gets its **placeholder retired rather than split**: if its only pane is one seahelm stood up itself this run (`StationManager.wasAutoCreated`, true for `tree(for:)`/`replacementTree` and false for a layout restored from config) and nobody has used it — no agent, no activity, `Station.showsOnlyPrompt == true` — `retirePlaceholderPane` destroys it and kills its seahelmd session, so the mover becomes the whole tree instead of landing beside an empty terminal. `showsOnlyPrompt` returns `nil` for "unknowable" (asleep, or an unreadable surface) and the policy treats nil as used: the pane is about to be thrown away, so it gets no benefit of the doubt. A worktree whose last pane left gets a replacement pane via `StationManager.replacementTree`, which claims a *free* seahelmd session name — the departed pane kept the worktree's canonical one (seahelmd has no rename), so reusing it would point two panes at one live session. **Two triggers, both keyed on that cwd.** The untracked-worktree check above only holds until discovery catches up, and the sweep runs every 5s (`branchRefreshTimer`) — an agent whose directory change is not itself a tool call (Codex's `/cd` fires no hook) reports its new cwd long after. So `onPaneWorktreeResolved` fires on *every* event naming a pane, and `TabCoordinator.followAgentToWorktree` moves the pane whenever the resolved worktree differs from its live `AgentRegistry` attribution. It is deliberately not edge-cached: the owner compares against the authoritative copy, so a move that could not complete yet is simply retried on the next event. Subagent events (`agent_id` present) are excluded — one running elsewhere must not drag its parent's pane.

**Two gates on the follow** (`TabCoordinator.shouldAutoFollow`, pure and unit-tested), because a cwd on its own says less than it looks like it does. *Same repo:* a pane follows its agent between worktrees of the repo it is working on; a cwd in an unrelated repo is a visit. This is also the only thing separating the pane's own agent from an agent it merely spawned — `SEAHELM_PANE_ID` (and the `SEAHELMD_SESSION` the hook falls back to) is inherited by **every descendant process**, so a test harness that stands up its own agent in a generated app directory reports events under the pane's id with a cwd of its own. *Cooldown:* after any move, auto-follow holds off for 10 minutes (`autoRehomeCooldown`). An agent's cwd bounces while it works — Claude runs `cd <worktree> && …` for one tool call and is back at the repo root for the next — and following both directions walked the pane in and out, leaving a replacement pane behind on the source at every departure. The cooldown delays, it does not pin: once the agent has settled elsewhere the next event still moves the pane. The same-repo gate also sits on the pending-transfer path in `performPaneRehome`.

Hook-driven repo auto-add (`handleNewWorktreeFromHook`) has its own two guards for the same reason: `isEphemeralRepoPath` (tmp/caches) and `isToolStateRepoPath` (any repo root inside a hidden directory, e.g. `~/.amuxd/teams/<id>/apps/<id>`). Auto-add is silent and `workspacePaths` is never pruned, so without them every app a daemon generates becomes a permanent project. Explicit Add Repo is the user's call and consults neither.

Attribution is otherwise a continuous function of the agent's cwd, so an *undo* of an automatic move is not offered: it would only change seahelm's view, and the agent's next event would move the pane straight back. `seahelm pane move <pane> <worktree>` remains the manual path — it matters for panes that report no hooks at all, and it starts the same cooldown, so a manual correction stands rather than being reverted by the next event.

**Pane fork:** auto-follow is gone: a pane whose agent goes into another worktree stays filed where it was and its chrome title shows where the agent is (`PaneAwayIndicator`, from `Station.hookLocation`). The user can then *fork* it there: the header's branch button (shown only while the focused pane's agent is away in a tracked worktree), or `seahelm pane fork <pane> [worktree]` (`pane.fork`). `TabCoordinator.forkPane` sends the original pane Esc (`Station.interruptTurn`): its turn stops, but its process, seahelmd session and transcript all stay. It then starts `claude --resume <id> --fork-session` (`AgentSessionRef.forkCommandLine`; id from `config.agentSessions`, plus the yolo flag when `agent_yolo`, and `--name <destination branch>` — a fork copies the transcript, title included, so without its own name it read exactly like the pane it came from; claude writes the name as a `custom-title`, which `SessionTitleLookup` prefers) in a detached seahelmd session on a free name in the destination, and files a new pane on it there, retiring the destination's placeholder if it is one. The fork waits at its prompt. Claude finds a session by id from any directory, so no transcript copying is needed. Claude only: other agents have no `forkArgv` row.

**Auto-fork into a new worktree:** where the agent *is* comes from its tool calls as well as its hook `cwd` (`AgentWorkLocation`). Claude Code resets the shell to the project directory after any command that leaves it, so an agent working in a sibling worktree (`git worktree add ../repo-x`) reports the main checkout on every event and writes `cd ../repo-x && …` into each command instead. `WebhookStatusProvider` keeps, per pane, the directory of the latest tool start that names one (a leading `cd`, or an Edit/Write path); a shell command with no `cd` clears it; events that name no place (Stop, prompts, reads) leave it alone. Status attribution still follows the cwd. The provider also records, per pane, the worktrees its agent *created* (`AgentWorkLocation.createdWorktree`: `git worktree add [opts] <path>` anywhere in a Bash command, resolved past a `cd`/`git -C`, or EnterWorktree's `<cwd>/.claude/worktrees/<name>`). When the agent's location is a tracked worktree it created and the pane is filed elsewhere, `TabCoordinator.autoForkIntoCreated` forks it there without being asked (`PaneFork.shouldAutoFork`: once per pane and destination, `auto_fork_panes`, default true). The original pane stays, its turn stopped. A `cd` into a worktree someone else made is a visit and forks nothing — that includes an agent told to go work in an existing worktree. The automatic fork gets a first message telling it to carry on in its new directory (`PaneFork.continuePrompt`, passed as claude's positional prompt), and it does not take focus. The record is in memory, so a worktree created before a relaunch no longer counts.

**Pane exec:** `pane.exec` / `seahelm pane exec <pane> [--timeout MS] <command…>` runs a shell command and waits, returning its exit code and the output the pane shows for it; `pane.run` stays the "type + Enter" verb for anything (agent TUIs included). It only runs at an empty zsh primary prompt, and the shell itself decides (`ShellRunIntegration`). `GhosttyBridge.configureShellIntegrationEnvironment` points zsh's `ZDOTDIR` at `~/.config/seahelm/shell/zsh`, whose `.zshenv` sources Ghostty's own (which restores the user's `ZDOTDIR`) and then `seahelm-run.zsh`. That script keeps `~/.config/seahelm/run/<session>.prompt` (`"<seq> <last status>"`) present exactly while the shell sits at its prompt (precmd writes it, first in line so `$?` is intact; preexec removes it), and binds `_seahelm_run` to the private key `ESC[9013~`. The app spools the command to `<session>.cmd` and presses that key through seahelmd; the widget takes it only if `BUFFER`/`PREBUFFER` are empty and `CONTEXT == start` (writing `.claimed` with the prompt's seq and line count) and otherwise hands it back (`.refused`, the draft untouched). Completion is `.prompt` returning with a higher seq. Nothing needs a Ghostty surface, so off-screen and asleep panes work. Output is cut from `seahelmd history` between the command's echo (matched across soft-wrapped rows, whitespace ignored) and the returning prompt (`PaneExecOutput`). Shells started before this, and non-zsh shells, never write `.ready` and are refused. Exit codes: the command's own, 124 when it outlives `--timeout` (it keeps running), 2 for a refusal.

**Status detection pipeline:** `StatusPublisher` (background queue, 2s timer) → `readViewportText()` (with `ghosttyLock`) → `StatusDetector.detect()` → `DebouncedStatusTracker` → `WorktreeStatusAggregator` (main queue) → `AgentRegistry` → UI delegates. Every pane is polled every cycle: the preferred-worktree stride (others every 3rd cycle) exists but the preferred set is always empty.

**PR and CI on the fleet:** `WorktreePRStore` asks GitHub once per repo per minute (GraphQL, so a token is required — none means no request) for the 30 most recently updated PRs with their head branch, state, draft flag, review decision and the head commit's check rollup, and files them by branch (`WorktreePRStatusParser`; PRs from forks skipped). `buildWorktreeRowInfos` reads it for every worktree but main and the integration checkout: the row's second line shows `#12 ✓ approved` (✓ passing / ✕ failing / ● running; `merged`, `closed`, `draft` spelled out), the context menu offers *Open Pull Request*, and `fleet.groups` items carry it as `pr` for the web list. A failed fetch keeps the last answer and retries after 5 minutes.

**Unseen completion:** a pane whose turn ends (`running → idle`, at the point `deliverPaneStatusChange` announces it) while its worktree is not on screen in the frontmost app gets `PaneInfo.unseenCompletion` (`AgentRegistry.setUnseenCompletion`, published as `pane.unseen_changed`). It is not a status: everything that reasons about the agent still sees `.idle`; only the fleet draws it — a blue ● dot, its own "Finished" group just under "Needs input" in group-by-status, and in the web client the `unread` state ranked after failed and before running when a worktree opens. It clears when the worktree comes on screen (selection change, app activation), when a remote client shows the pane (`pane.seen`), or when the agent moves on (`UnseenCompletion.clears`).

**Worktree setup hook:** a repo's `.seahelm/setup.sh` (the new worktree's own copy, else the main checkout's, so an untracked script still applies) runs in a new worktree's first pane before its agent: `WorktreeSetupHook.launchLine` makes the detached session's command `<setup> && <agent>`, so a failed setup leaves the pane at the shell with the script's error on screen and no agent. The script runs in the new worktree with `SEAHELM_WORKTREE` and `SEAHELM_REPO_ROOT` set; an executable script runs by its shebang, anything else through `sh`. The opening brief waits up to 15 minutes for the agent when a setup ran. Worktrees made from the Cmd+N dialog (no agent) run the setup alone.

**First Mate autopilot**: an agent session of its own — Claude Code (permission allowlist, `--permission-mode default`) or Codex (workspace-write sandbox with network, `--ask-for-approval on-request`), `autopilot_agent`, switching replaces the session (`FirstMatePane`: seahelmd session `seahelm-first-mate`, directory `~/.config/seahelm/first-mate/` with a managed `CLAUDE.md`, a `.claude/settings.json` permission allowlist, and the user's `standing-orders.md`), woken by rules in each repo's `.seahelm/automations.yml` (`AutomationConfig`, parsed with Yams; built-in `fix-ci` / `cleanup-merged` when a repo has none; a file that does not parse stops that repo rather than falling back). `AutopilotCoordinator` (owned by `TabCoordinator`, off unless `autopilot_enabled`) turns `WorktreePRStore` changes into `ci.failed` (an observed edge only) and `pr.merged` (once per PR, persisted in `AutopilotLedger`) events, matches rules (`AutopilotEngine`: trigger, branch filter, `max_attempts` per PR per day), queues the prompts and hands them over when First Mate is idle and outside quiet hours; the user's own messages go in at once. Everything is written to `audit.jsonl` (`AutopilotAudit`). First Mate is registered in `AgentRegistry` but filtered out of the fleet, island, command index and `pane.list`, and its outcomes return early from `onOutcome` — none of the fleet's notifications apply; `StatusPublisher.pin` scans it without a split tree. Policy: a control call whose `_meta.caller` is First Mate's session is classified by `AutopilotPolicy` (reads open; `pane.run/send_text/send_keys` = `message_pane`, `worktree.create` = `start_agent`, `worktree.delete` = `delete_worktree`; anything else refused with -32040) and gated by `AutopilotCoordinator.gate`: the level is the strictest of the rules First Mate is handling (plus the defaults once the user has spoken — talking cannot loosen a rule), `start_agent` also checks `max_concurrent_agents` and `pause_above_usage`; `ask` becomes an `.autopilotApproval` pending order (Island + Telegram card; dismissing it is a no), the router answers `{"queued": "approval"}`, and on approval the call runs off main with `_meta` stripped (`AutopilotCoordinator.asUser` — the router gates on `_meta.caller` alone, so left in, an approved call would be gated again and raise a fresh card) and First Mate is told the result. Settings ▸ First Mate (`SettingsViewController+FirstMate`, also from the dock's context menu): the switch and pause, the user's default level per action (`autopilot_autonomy`, laid under every rule via `AutomationConfig.defaults`), standing orders, and a per-project rules editor (`FirstMateRulesView`) that writes the repo's `.seahelm/automations.yml` only on "Save to repo" (`AutomationConfig.yaml()`; hand-written comments are not kept, and the page says so). Rules may carry `enabled: false`. Schedules: `on: {schedule: cron}` with a five-field `CronSchedule`, checked once a minute by the coordinator for every project (missed minutes are not caught up); the built-in `triage-issues` rule ships off. Proposals: `seahelm propose` (`autopilot.propose`, First Mate only) raises an `.autopilotProposal` card whose options each carry an action First Mate could request itself and that is not set to deny — picking one runs that action as approved, "Not now" runs nothing; First Mate is told which. Chat: with First Mate on, prose in a chat bound to no pane goes to First Mate (`CommandHost.sayToFirstMate`, before the one-pane auto-bind) and `/mate [text]` unbinds a chat back to it; the coordinator remembers which chats asked and sends First Mate's answer (`lastAssistantMessage` at the end of its turn) to them, and every `.action` audit line goes to the default Telegram chat. Web: `autopilot.state` (state, First Mate's pane, its cards; refused to First Mate itself and to share links) is fetched after auth and pushed as an `autopilot.state` notify on every change (`.firstMateStateChanged` → `HostGatewaySession.pushFirstMateState`, paired clients only); `autopilot.answer {card, option}` answers a card through the same path as the island. seahelm-web shows a ⎈ icon in the list's title bar (state colour; amber with a count when cards wait) that opens First Mate's pane like any pane — accent title strip, its cards above the composer — while its row never appears in the list. UI: `FirstMateDockView` at the foot of the fleet column (where the shortcut strip was; on hover it shows only pause) toggles `FirstMateView` in the dashboard's center overlay — its terminal. The audit log has no view in the app (it is `audit.jsonl`, and `.action` lines go to Telegram).

**Auto-update:** Sparkle 2 (`Sources/Update/UpdateDriver.swift`, `Sources/App/UpdateCoordinator.swift`). `UpdateDriver` implements `SPUUserDriver` so updates render in the inline `UpdateBanner` instead of Sparkle's modals; it stashes each pending Sparkle reply block until the matching banner button is clicked. There is one appcast per CPU arch (we ship arch-specific zips and Sparkle has no arch filtering), so the feed URL is supplied at runtime by `UpdateCoordinator.feedURLString` rather than baked into Info.plist. `SUPublicEDKey` comes from the `SPARKLE_PUBLIC_ED_KEY` build setting; empty means Sparkle refuses to start. `scripts/package_release.sh` signs Sparkle's nested helpers (Autoupdate, Updater.app, `Downloader.xpc`, `Installer.xpc`) inside-out, then generates and signs `dist/appcast-<arch>.xml` from the final notarized zip using `SPARKLE_PRIVATE_KEY`.

**Focus management:** `GhosttyNSView` overrides `becomeFirstResponder`/`resignFirstResponder` to call `ghostty_surface_set_focus()` and apply visual shadow state. `mouseDown` calls `makeFirstResponder(self)`. Split pane operations defer `makeFirstResponder` via `DispatchQueue.main.async` to run after Ghostty's own deferred focus handling.

**Thread safety:** `ghosttyLock` (NSLock) serializes all Ghostty C API calls between the background status poll and main-thread input. Key input deliberately does NOT hold the lock (Ghostty is internally thread-safe for keys, and holding it would deadlock on synchronous callbacks).

**Window key handling:** `SeahelmWindow.performKeyEquivalent` handles split pane shortcuts (Cmd+D / Cmd+Shift+D split, Cmd+Option+Arrow move split focus, Cmd+Ctrl+Arrow resize) before menu key equivalents. `sendEvent` intercepts Escape.

## Agent Orchestration ("the fleet")

The structure is plain: one app ⊃ many **projects** (repos) ⊃ many **worktrees** ⊃ many **panes**, each pane running an **agent**. `AgentRegistry.shared` is the app-wide source of truth across all panes. (Note: `Station` is taken for the surface wrapper, so it names none of these tiers.)

This used to be a nautical metaphor — Ship / Deck / Cabin / Sailor for app / repo / worktree / pane — and older commits, branch names and issues still speak it. The rename dropped it because `Sailor` in particular had come to mean two things at once, the pane and the agent inside it, which is why the types below split along that line rather than mapping one-to-one onto the old names.

- **Pane / agent model** (`Sources/Core/`): `AgentType` = agent kind (claudeCode, codex, openCode, gemini, cline…), `AgentStatus` = state enum (owns the status-dot color), `PaneInfo` = per-pane snapshot, `PaneReducer` = pure `(old + inputs) → (new snapshot + delta)` (extracted from `AgentRegistry.updateStatus`), `AgentChannel` = protocol for talking to a pane's terminal (`SeahelmdChannel` is the universal fallback via the `seahelmd` CLI; `HooksChannel` is the richer path for agents that report structured events). Note `PaneStatus` is a different type: the per-pane snapshot the worktree rollup consumes, in `Sources/Status/`.

- **Manifest engine** (`Sources/Status/`): data-driven detection ported from a sibling project. `AgentManifest` is a JSON schema of priority-ordered regex rules/gates/process matchers (bundled under `Sources/Status/Manifests/`, overridable at `~/.config/seahelm/agents/<id>.json` — user override wins by id/alias). `ManifestStore` compiles them; `ManifestEngine` evaluates a terminal snapshot. The `*Decoder` files are the newer "signalman" seam: `SignalDecoder` translates one raw source into a unified `NormalizedEvent`; `ScanDecoder` wraps `StatusDetector` (screen-scan channel), `HookDecoder` maps webhook events. These feed the reducer/ingest pipeline broadcast through `EventHub`.

- **Control socket & CLI** (`Sources/Core/`): `ControlSocketServer` listens on a 0600 Unix socket at `~/.config/seahelm/seahelm.sock` speaking newline-delimited JSON-RPC (`ControlProtocol` = transport-free router + `ControlDataSource` seam; `SeahelmControlDataSource` bridges it to live app state). `SeahelmCliInstaller` writes `~/.local/bin/seahelm` (python3 wrapper) so agents run e.g. `seahelm pane run <id> npm test` — this backs the `seahelm` skill. The chat/Helm command language lives in `Sources/Core/Command/` (design: `docs/command-redesign.md`): `CommandSpecs` is the verb table every other piece is generated from, `CommandParser` is pure (text + `FleetIndex` → `CommandLine`), `CommandExecutor` is the one place a verb has meaning, and `CommandSession`/`CommandSessionStore` hold what each Telegram chat and mail thread is talking to — the desktop's session is the dashboard selection. Panes are addressed by a stable `#n` from `PaneHandleRegistry`, worktrees and repos by `@name`. `EventHub` is the fan-out broker (bounded ring buffer, `events_after` replay) for control-socket subscribers. `pane.send_keys` presses real keys (`KeyChord`: letters, digits, punctuation, F-keys, nav keys, ctrl/alt/shift) — never text, since text is the paste path and a TUI ignores a pasted digit; alt is ESC-then-key for characters (Ghostty treats Option as a composing key unless `macos-option-as-alt`) and the xterm `ESC[1;3x` form, written into the seahelmd session, for keys like alt+left. **Presence:** the CLI sends `params._meta = {caller: $SEAHELM_PANE_ID, note}` on every call; for pane-acting methods (`ControlRouter.presenceMethods`, and the pane a `pane.split` creates) `PanePresence` shows a pill on the target pane naming the calling pane's agent and `#n` handle plus the `seahelm --note …` text, with an accent frame, for 6s after the last call. Clicking it focuses the caller. Display only — it never changes routing.

- **Hooks installers** (`Sources/Core/*HooksSetup.swift`, `*Installer.swift`): non-destructively install per-agent shims so third-party agent CLIs report lifecycle events back to seahelm. `SeahelmHookInstaller` writes `~/.local/bin/seahelm-hook` (the shared bridge, `/bin/sh` + `nc -U`: the socket only, fire-and-forget, nothing on stdout — the HTTP webhook and Stop-hook relaying are gone); `ClaudeHooksSetup`/`CodexHooksSetup`/`CursorHooksSetup`/`OpenCodePluginInstaller` wire that bridge into each tool's config. `AgentHookInstaller` installs them at launch, limited to `enabled_hook_agents` when set (all of them otherwise).

- **FirstMate** (`Sources/Core/FirstMate*.swift`): an autonomous supervisor reacting to agent status transitions. A green-zone/red-zone action model (watchWaiting, watchError, inspect, autoCommit, suggestNextOrder, broadcastOrder, integrationReport); `FirstMateConfig` holds user policy; `FirstMateCoordinator` (main thread) consumes status edges, routes green-zone actions to side effects and red-zone actions to the `PendingOrdersQueue`. Watches idle/blocked/errored agents and either auto-handles or surfaces them for approval.

- **Usage** (`Sources/Usage/`): `CodexUsageSummaryProvider` reads Codex's rate limits and today's tokens from its session logs, `ClaudeUsageSummaryProvider` only the statusline cache below (it does not scan `~/.claude/projects`: a day of transcripts runs to hundreds of MB, and re-parsing them every minute kept the refresh from ever finishing, so the 5h/7d readout never appeared); `UsageSummaryStore` refreshes both on a background timer and hands the snapshots to `IslandModel` — `UsageSummaryFormatter.readouts` turns them into `UsageReadout`s, which the closed pill rotates one window at a time (left wing, yielding to pending orders) and the opened header shows in full on the title row. Claude only reports rate limits inside its statusline payload, so `ClaudeStatuslineBridgeInstaller` (run at window setup) wraps the user's `statusLine` command to tee that payload into `~/Library/Caches/seahelm/claude-statusline.json`.

- **seahelm-core** (`seahelmd/crates/core*`, design: `docs/status-core-port.md`, crate contract: `docs/core-crates.md`): the status detection above, ported to Rust as a headless per-user service so non-macOS clients have it. `seahelm-core serve` listens on `~/.config/seahelm/core.sock` (same JSON-RPC shape as the app's socket) and reads each registered pane's screen with `seahelmd snapshot` (viewport, title, OSC 9;4 progress, the OSC 7501 root record — seahelmd now keeps 7501 itself and answers its support query while detached). Panes are keyed by seahelmd session name; a client's own id is an alias. The app does not use it yet. Hooks reach it without the app: the app's bridge `seahelm-hook` (v7) sends every payload to the core's socket as well as the app's, and on a machine without the app `seahelm-core install-hooks` wires Claude Code and Codex to `seahelm-core hook <source>`, the cross-platform bridge (named pipe on Windows; it leaves events already running `seahelm-hook` alone, so nothing arrives twice). `seahelm-core shadow --follow-app` mirrors the app's panes into it and logs disagreements to `~/.config/seahelm/core-shadow.jsonl`. The GPUI client (`clients/gpui`) registers its panes with it. It also holds the **cards** — every "waits on you" item (agent questions, screen choices, suggestions; client-raised reports and First Mate approvals/proposals) — in one queue (`core-registry/src/cards.rs`), served as `cards.list` / `cards.answer` / `cards.dismiss` / `cards.raise` / `cards.clear` and pushed as `cards.changed`. The core performs every answer itself through seahelmd (typed option, arrow keys from the dialog's cursor, multi-select ticks, follow-up questions, the review page's Return), so renderers never press keys; a raised card's answer goes back to its owner as `card.answered`. The GPUI client draws the selected worktree's cards above its terminals. The core can also run **First Mate** (`seahelmd/crates/core/src/first_mate/`, same session, directory, rules, ledger and audit as the app's), but only when `config.json` has `autopilot_owner: "core"` as well as `autopilot_enabled`, and only while it holds `first-mate/owner.lock`; without that key the app keeps First Mate. First Mate's `seahelm` command is then a shim onto `seahelm-core cli`, and the core gates and performs its actions itself (`actions.rs`). It also keeps every pane's **message timeline** (`crates/core-messages`: user prompts, tools, decisions, turn edges, final messages, and the prose between tool calls read from the agent's transcript), served as `message.snapshot` / `message.history` / `message.subscribe` and compared against the app's with `seahelm-core compare-messages`. It also runs the **command language** (`crates/core-command`, `command.run {text, context}`): cut on 2026-11-04 to `/go #n|@worktree|mate`, `/new`, `/status`, `/show`, `/help` plus prose for whoever the conversation talks to, with no confirmations; the caller keeps the binding (see `docs/command-redesign.md` §0). The app ships `seahelm-core` beside seahelmd (Contents/Resources/bin), starts it, mirrors its panes and worktrees into it every 2 s, and runs every command entry (Helm line, Telegram, mail, chat buttons) through `command.run` (`CoreLink`, `MainWindowController.routeCommand`), taking the core's `#n` handles and adopting sessions the core starts for `/new`; `Sources/Core/Command/`'s executor is only the fallback when the core does not answer. Plan and status: `docs/first-mate-core.md`. To test it, isolate everything: scratch `HOME`, `SEAHELM_CORE_SOCKET`, and `SEAHELMD_DIR` — seahelmd session names are machine-wide, and a scratch core taking First Mate would replace the live app's `seahelm-first-mate` session. When testing with a real agent in a scratch seahelmd session, point `SEAHELM_SOCKET_PATH` somewhere dead: seahelmd sets `SEAHELMD_SESSION`, so the agent's hooks otherwise reach the live app and land on the worktree's first pane.

## Keyboard System (modal)

The modal Vim/which-key system described in `docs/keyboard-redesign.md` (NORMAL/INSERT `KeyboardMode`, `KeyboardModeController`, `Keymap`, `LeaderMenu`) is gone, and so is the last transient `KeyboardSubstate` — it only ever marked the inline create form, which went with the sidebar composer. `Sources/App/KeyboardMode.swift` now holds just `FocusDirection`. Whether bare keys navigate is decided by who owns focus (`RegionFocusController`); `GlobalKeymap` centralizes window-level Cmd shortcuts, and `SeahelmWindow.performKeyEquivalent` (below) still handles the split-pane Cmd shortcuts.

## Key Technical Details

- **Swift 5.10**, macOS 14.0+ (Sonoma), AppKit (not SwiftUI)
- **Ghostty C interop** via `seahelm-Bridging-Header.h` → `ghostty.h`; `GhosttyKit.xcframework` provides `libghostty`
- Links against: Metal, QuartzCore, IOSurface, Carbon, UniformTypeIdentifiers, libghostty, libc++
- SPM dependencies: `CodeEditSourceEditor` (+ `CodeEditLanguages`) for the embedded code editor; otherwise system frameworks + Ghostty
- Delegate pattern used throughout (not Combine/async-await for UI updates)
- `GhosttyBridge.shared` is the singleton entry point for all terminal operations
- `StationRegistry.shared` is the global surface lookup table (surface ID → Station)
- `AgentRegistry.shared` is the single source of truth for agent state (status, messages, activity events)
- Tests use XCTest with `@testable import seahelm`; test files in `Tests/` directory; no external test dependencies
- Config uses `decodeIfPresent()` throughout for backward compatibility with older config files
- `ghostty/` directory contains the vendored Ghostty source (read-only reference, not built from here)
